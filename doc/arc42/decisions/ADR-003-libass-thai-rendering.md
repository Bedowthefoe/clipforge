# ADR-003 — libass + .ass for Thai subtitle rendering

**Status:** Accepted
**Date:** 2026-05-24
**Deciders:** Operator

---

## Context

Thai script requires complex shaping — vowel marks stack above consonants, tone marks stack above vowels. Two FFmpeg paths exist for burning subtitles:

| Option | Pros | Cons |
|---|---|---|
| `drawtext` filter | Simple per-event API | FreeType-only (no HarfBuzz) → Thai glyphs render as boxes |
| `subtitles` filter (libass + .ass) | Full HarfBuzz Thai shaping; styles, positions, transitions | Need to generate .ass format |

## Decision

Use **libass via FFmpeg `subtitles` filter** with `.ass` files generated by [python-ass](https://github.com/chireiden/python-ass).

```python
import ass as ass_lib
doc = ass_lib.Document()
doc.play_res_x = video_width
doc.play_res_y = video_height
# add Style entries, Dialogue events
```

FFmpeg invocation:
```
ffmpeg -i input.mp4 -vf "subtitles=path.ass:fontsdir=/usr/share/fonts" -c:v libx264 ...
```

## Why

- **`drawtext` is structurally incapable of rendering Thai** — confirmed by visible-box failure in early POC tests.
- **libass uses HarfBuzz** complex-script shaping — this is what Thai needs (`mark` and `mkmk` GPOS features).
- **`.ass` format** supports the two-tier style we need: Speech (white + drop shadow, bottom) + KeywordPop (white + pink outline, italic, top).
- **`python-ass`** has a clean dataclass-style API; writing the file is trivial.
- libass picks up fonts from both `fontsdir=` AND fontconfig (`~/.fonts/`, `/usr/share/fonts/`).

## Consequences

- **All Thai text MUST go through .ass** — no `drawtext` for Thai. Confirmed banned in [02-constraints.md](../02-constraints.md).
- Font choice matters a lot (see ADR-009): the font's GPOS lookups must define mark-to-mark anchors well, or tone marks collide with vowels.
- We need word-aware line wrapping because Thai has no inter-word spaces: ADR-004 covers PyThaiNLP + `\N` line breaks.
- libass `wrap_unicode` works (libass 0.17+ with libunibreak) but breaks Thai anywhere — semantically wrong. We don't use it.

## Style implementation

In `subtitle.py::make_overlay_ass`:

```python
sp = ass_lib.Style()  # Speech
sp.name = "Speech"
sp.fontname = cfg.subtitles.font           # "IBM Plex Sans Thai"
sp.fontsize = auto-scale or explicit
sp.primary_color = white
sp.outline_color = white                   # invisible outline
sp.back_color = (0,0,0, semi-transparent)  # shadow color
sp.outline = 0                              # no border
sp.shadow = 10                              # drop shadow offset
sp.bold = True
sp.alignment = bottom-center
sp.margin_v, margin_l, margin_r set

kp = ass_lib.Style()  # KeywordPop
kp.name = "KeywordPop"
kp.outline_color = magenta (#FF1493)
kp.outline = 18                             # thick pink border
kp.italic = True
kp.alignment = top-center
```

## Revisit triggers

- If libass introduces a regression in Thai shaping (unlikely; libass 0.17+ is stable).
- If a non-libass alternative gains complex-script support comparable to HarfBuzz (e.g., a future native FFmpeg shaping filter).
- If we add support for non-Thai content where the .ass overhead is heavier than needed.
